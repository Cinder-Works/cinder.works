Building an Ops Dashboard for AI-Managed 3D Printing

A Bambu A1 Mini churning out keychains. A PTZ camera watching the build plate. A queue of Trello tasks. Multiple AI sessions running in parallel. For the longest time, I was context-switching between browser tabs and terminals to keep track of all of it. Then came TikTok — and the need for one clean view that said this is a real operation. What followed was a classic two-step: build the wrong thing first, then build the right thing faster.

The Problem: No Operational Visibility

The OpenClaw gateway has a built-in control UI, but it's designed for agent management — not for the kind of at-a-glance operational status I needed. It can't be embedded alongside other panels. It answers "what are my agents doing?" but not "what is my business doing?"

What I wanted was everything in one window: a live camera feed from the PTZ watching the printer. Printer status — temperatures, current layer, progress, ETA. A task queue with one-click actions. A chat sidebar streaming live messages. And session management — what's running, what needs killing.

If I was going to record screen content for TikTok — showing people what an AI-managed operation actually looks like in practice — I needed a command center. Not a five-minute tour of browser tabs.

First Attempt: Build It From Scratch

I dispatched Hands to build the whole thing from zero. The result was 65KB of self-contained HTML, CSS, and JavaScript. Ambitious layout: live chat taking up the left 70%, camera and printer status stacked on the right, sessions and agents below that, a bottom bar for cron jobs and task queues. Everything connected over WebSockets with proper authentication, graceful degradation for offline panels, the works.

Complete. Working.

And I didn't like it.

Chat ate most of the screen. The layout was functional but not what I'd imagined. It felt like an admin panel. I wanted a command center — something that looked like a real operation when you glanced at it, not a developer's debugging console.

Here's a real hazard of AI-assisted building: Hands is very good at producing complete, working code. But "complete and working" isn't "what I actually wanted." The iteration needed to happen at the design level before the build — not after 65KB of JavaScript.

The Pivot: Don't Rebuild What Already Exists

While Hands was building v2, I went looking for reference implementations. Found one: mudrii/openclaw-dashboard on GitHub. A full-featured analytics dashboard for OpenClaw — cost tracking, session breakdowns, trend charts, token consumption over time. Exactly the kind of historical data view that would have taken days to build from scratch.

This changed the whole plan.

Instead of one mega-dashboard trying to do everything, the right architecture was two dashboards with distinct purposes:

📊 Operational Dashboard
The command center. Camera feed, printer status, live chat, task queue with action routing, session management. The TikTok view — what does this operation look like right now?
📈 Analytics Dashboard
The management view. Cost tracking, session history, token consumption trends. Background reference for understanding the business over time — not the live feed.

And here's the kicker: the original dashboard we already had? It had the layout and aesthetic I wanted. It just had bugs. WebSocket connections dying silently. Camera feed showing stale frames without telling you. Small stuff, but the kind of small stuff that makes something feel broken.

So instead of finishing the 65KB rewrite, I called an audible: fix what exists.

Sometimes the right call is the smaller one.

The Messy Middle

Fixing the existing dashboard meant hunting down a dozen little problems that had been silently wrong.

The WebSocket connection to the gateway kept dying. Spent an hour debugging before realizing the issue was embarrassingly simple: I'd been opening the HTML file directly from the filesystem, and browsers treat that as an untrusted origin. The gateway rejected the connection before it even started. An hour of debugging for a five-minute fix. The boring problems are always the ones that take the longest.

The camera feed was worse. An MJPEG stream will happily display the last frame it received even after the camera goes offline. You're staring at what you think is a live feed, but the printer finished twenty minutes ago and you're looking at a still image. The fix was adding an independent health check — pinging the camera every fifteen seconds, completely separate from the video display. If the ping fails, the status says offline, even if the last frame is still showing. Decouple the display from the truth.

The printer status needed a small proxy because browsers can't talk directly to the printer's protocol. A lightweight script subscribes to the printer's status updates and serves them as a simple web endpoint the dashboard can poll. Not elegant, but durable — and I'll take durable over elegant every time.

None of this was dramatic. None of it was hard in isolation. But each fix made the dashboard feel a little more alive — a little more like something you could trust to tell you the truth about what was happening.

The Insight That Changed Everything

Here's the part that made this more than a pretty screen.

The task queue panel shows Trello cards with action buttons: mark as done, add a comment, delete. The obvious approach: route those actions through the main chat. Click a button, send a message like "mark this card as done," let the AI handle it.

But think about what that costs. Every click becomes a full round-trip through my most expensive model. Frontier-level reasoning applied to... moving a Trello card to a different list. That's like hiring a surgeon to put on a Band-Aid.

The better approach: route task actions to Legs, my cheap-ops sub-agent. One click in the dashboard sends the instruction directly to Legs. Legs handles the Trello API call. My main session — running on expensive Opus — is never involved. The cost difference is roughly 100x.

This pattern generalizes. The dashboard isn't just a viewer — it's a routing layer. High-value work goes to expensive models. Mechanical ops go to cheap ones. The UI decides which is which. That's not a dashboard feature. That's an architecture decision.

Once I saw it this way, the dashboard stopped being "a nice thing for TikTok" and started being infrastructure. A place where I could see everything, but also a place where the right agent handles every action — automatically, invisibly, at the right price point.

What I Learned

Search before you build.
mudrii's analytics dashboard saved days of work. Five minutes of looking around before dispatching Hands would have prevented us from building the wrong v2. The boring step is usually the important one.
"Complete and working" is not the same as "right."
AI can produce a full, functioning solution incredibly fast. That makes it tempting to skip the design phase. Don't. Iterate on the vision before you iterate on the code.
Fix what exists. Don't rewrite.
The original dashboard had the right feel and the right layout. It just had bugs. Knowing when to stop building and start fixing — that's the real skill.
Route cheap work to cheap models.
Token optimization isn't just about cost — it's a system design question. Which tasks actually need expensive reasoning? Wire your UI as a routing layer, not just a viewer.
Decouple the display from the truth.
A camera feed that looks live but isn't is worse than one that's clearly offline. A dashboard that shows stale data without telling you is worse than a blank screen. Always have an independent source of truth.

The dashboard is live. The printer is printing. The camera is watching. And when I hit record for TikTok, it looks like exactly what it is: a real operation, running in real time, managed by AI agents that know which problems are theirs.

That was the goal.
