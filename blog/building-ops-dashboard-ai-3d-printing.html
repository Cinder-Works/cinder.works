Building an Ops Dashboard for AI-Managed 3D Printing

A Bambu A1 Mini churning out keychains. A PTZ camera watching the build plate. A queue of Trello tasks. Multiple AI sessions running in parallel. For the longest time, I was context-switching between browser tabs and terminals to keep track of all of it. Then came TikTok — and the need for one clean view that said this is a real operation. What followed was a classic two-step: build the wrong thing first, then build the right thing faster.

The Problem: No Operational Visibility

The OpenClaw gateway has a built-in control UI, but it's locked behind X-Frame-Options: DENY. You can't embed it. You can't compose it with other panels. And even if you could, it's designed for agent management — not for the kind of at-a-glance operational status I needed.

What I wanted: a live camera feed from the PTZ watching the printer. Printer status — nozzle temp, bed temp, current layer, progress, ETA. A task queue showing what's pending with one-click actions. A chat sidebar streaming live messages. And session management — what's running, ability to kill sessions that need killing.

The camera was already accessible: http://192.168.0.248:8080/stream serves a plain MJPEG stream. The printer talks MQTT, but browsers can't speak MQTT over TLS — that needed a proxy. The gateway WebSocket was the tricky piece.

And if I was going to record screen content for TikTok — showing people what an AI-managed operation actually looks like in practice — I needed all of this in one window. A command center. Not a five-minute tour of browser tabs.

First Attempt: Build It From Scratch

I dispatched Hands to build the whole thing from zero. The result was dashboard_v2.html — 65KB of self-contained HTML, CSS, and JavaScript. Ambitious layout:

┌─ HEADER: version · health · channels · heartbeat ────┐ ├─ LEFT 70% ─────────┬─ RIGHT 30% ────────────────────┤ │ 💬 LIVE CHAT │ 📷 PTZ CAM │ │ [session switcher] ├────────────────────────────────┤ │ message history │ 🖨️ BAMBU STATUS │ │ [streaming text] │ temps/layer/progress/ETA │ │ [send input] ├────────────────────────────────┤ │ │ ⚡ SESSIONS (kill/view) │ │ ├────────────────────────────────┤ │ │ 🤖 AGENTS (click = switch) │ ├─ BOTTOM BAR ───────┴────────────────────────────────┤ │ CRON | HEARTBEAT | TASK QUEUE | OPERATIONS │ └──────────────────────────────────────────────────────┘

Custom WebSocket client with challenge/response auth, streaming chat deltas, session switching, token management via localStorage, graceful degradation for all the "panel offline" states. Complete. Working.

And I didn't like it.

Chat ate 70% of the screen. The layout was functional but not the aesthetic I'd imagined. It felt like an admin panel. I wanted a command center.

Here's a real hazard of AI-assisted building: Hands is very good at producing complete, working code. But "complete and working" isn't "what I actually wanted." The iteration needed to happen at the design level before the build — not after 65KB of JavaScript.

The Pivot: Don't Rebuild What Already Exists

While Hands was building v2, I went looking for reference implementations. Found one: mudrii/openclaw-dashboard on GitHub. A full-featured analytics dashboard for OpenClaw — cost tracking, session breakdowns, trend charts, token consumption over time. Exactly the kind of historical data view I'd have needed to build from scratch.

This changed the whole plan.

Instead of one mega-dashboard trying to do everything, the right architecture was two dashboards with distinct purposes. The mudrii dashboard for analytics and cost tracking — background management view. And the original dashboard.html we already had — operational command center, camera, printer, live chat, task queue. The TikTok view.

The original dashboard.html already had the layout and aesthetic I wanted. It just had bugs. So instead of completing dashboard_v2.html, I called an audible: fix what exists.

Sometimes the right call is the smaller one.

Technical Challenges (and How We Solved Them)

1. WebSocket Origin Restrictions

The biggest initial blocker. Opening dashboard.html directly from the filesystem (file://) means WebSocket connections to the gateway get rejected — the gateway validates request origins, and file:// doesn't match any expected http:// or https:// origin.

The fix was embarrassingly simple once you know to look for it:

Serve the dashboard over HTTP: 

cd workspace && python3 -m http.server 8082

Add the origin to gateway config: 

{
  "gateway": {
    "controlUi": {
      "allowedOrigins": ["http://127.0.0.1:8082"]
    }
  }
}

This is the kind of thing that burns an hour when you don't know where to look. Once you know — five minutes. I'm writing it down so it takes you five.

2. WebSocket Client ID Validation

The OpenClaw gateway uses a challenge/response auth flow on the WebSocket. Client sends a client ID, server responds with a challenge nonce, client signs it with the gateway token. Standard handshake.

The problem: getting the client ID wrong means silent connection failures. The WebSocket connects, the gateway ignores all your requests, and you stare at a blank dashboard wondering what you've done wrong. Ask me how I know.

The correct client ID is gateway-client (visible in the control-ui source). The full connection flow: 

// 1. Connect
const ws = new WebSocket('ws://127.0.0.1:18789');

// 2. On open, identify
ws.send(JSON.stringify({
  type: 'hello',
  clientId: 'gateway-client'
}));

// 3. Gateway responds with challenge
// { type: 'challenge', nonce: '...' }

// 4. Sign and respond
ws.send(JSON.stringify({
  type: 'auth',
  token: gatewayToken,
  nonce: challengeNonce
}));

// 5. Now you can make RPC calls

We also added a watchdog timer — if the connection is stuck in "Connecting..." for more than 10 seconds, it logs an error and resets. Silent hangs are worse than visible failures. Always.

3. MJPEG Camera Feed Health Checking

The PTZ camera serves a standard MJPEG stream. An <img> tag pointing at the URL "works" in that it displays frames — but detecting whether the stream is actually alive is surprisingly tricky.

The naive approach: 

cameraImg.onload = () => setCameraStatus('online');
cameraImg.onerror = () => setCameraStatus('offline');

This doesn't work reliably. onload fires once when the connection opens. onerror often doesn't fire when the stream drops — the browser just shows the last frame or a broken image icon. You're looking at a "live" feed that died three minutes ago.

The solution: periodic health checks using a fetch probe, decoupled from the display element entirely: 

async function checkCameraHealth() {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 3000);

  try {
    const response = await fetch('http://192.168.0.248:8080/stream', {
      method: 'HEAD',
      signal: controller.signal
    });
    clearTimeout(timeout);
    setCameraStatus(response.ok ? 'online' : 'offline');
  } catch (e) {
    setCameraStatus('offline');
  }
}

setInterval(checkCameraHealth, 15000);
checkCameraHealth(); // Run immediately on load

Every 15 seconds, probe the stream URL with a HEAD request. The <img> tag just shows whatever it can. The health check tells us the ground truth. Decoupled. Durable.

4. Printer Status via MQTT Proxy

Browsers can't speak MQTT over TLS directly. The Bambu A1 Mini uses MQTT on port 8883 with certificate-based auth — nothing a browser WebSocket can reach.

Solution: a small Flask proxy sitting between the dashboard and the printer: 

# bambu_dashboard_proxy.py (port 19000)
# Connects to Bambu MQTT, subscribes to printer status topic
# Exposes /status endpoint that returns latest state as JSON
# Dashboard polls every 5 seconds

The proxy subscribes to device/{serial}/report, parses the JSON payload, serves the latest state via a plain HTTP endpoint. The dashboard polls it. Simple, durable, no exotic dependencies.

The only drama was port conflicts — we went through 18791, 18792, and finally settled on 19000 after discovering what was already bound. The mundane problems are always the ones that take the longest to debug.

5. Session Management via Gateway RPC

Once the WebSocket connection is authenticated, the gateway exposes a full set of RPC methods:

sessions.list — all active sessions. sessions.delete — kill a session by ID. agents.list — all configured agents. chat.send — send a message to a session. chat.history — fetch message history. health — gateway health status.

The dashboard uses these to render a live sessions panel with individual kill buttons, and an agents panel where clicking an agent card switches the chat context to that agent's session. Point and click to talk to any agent.

The Token Routing Layer

Here's the part that made the ops view genuinely useful beyond looking good on camera.

The task queue panel shows Trello cards with action buttons: ✓ Done, 💬 Comment, 🗑️ Delete. The obvious approach: route those actions through the main chat. Send a message like "mark card X as done." Let the AI handle it.

But that burns expensive tokens. Every click becomes a full Opus round-trip. Trello card management does not need frontier-model reasoning.

The better approach: route task actions to Legs, my cheap-ops sub-agent running on gpt-5-mini. 

async function handleTaskAction(cardTitle, action) {
  const instructions = {
    done: `Mark Trello card "${cardTitle}" as DONE and move to completed list`,
    comment: `Add comment to Trello card "${cardTitle}": [prompt user]`,
    delete: `Delete Trello card "${cardTitle}"`
  };

  // Route to Legs via sessions_send (cheap gpt-5-mini, not Opus)
  await gatewayRpc('chat.send', {
    sessionId: 'agent:legs:main',
    message: instructions[action]
  });
}

One click in the dashboard triggers a sessions_send to Legs. Legs handles the Trello API call. My main session is never involved. The cost difference is roughly 100x.

This pattern generalizes: the dashboard isn't just a viewer. It's a routing layer. High-value work goes to expensive models. Mechanical ops go to cheap ones. Wire your UI accordingly.

Final Architecture

📊 dashboard.html :8082
Operational command center. Camera feed + health check. Printer status via proxy. Live chat over WebSocket to gateway. Task queue with action routing to Legs. Session management — list and kill.
📈 mudrii/openclaw-dashboard :8080
Analytics and cost tracking. Session history and breakdowns. Token consumption trends. The management view — background reference, not the live feed.
🖨️ bambu_dashboard_proxy.py :19000
MQTT subscriber to printer on :8883. Serves /status as JSON. Polled every 5 seconds by dashboard.

To run the ops view: 

# Terminal 1: serve dashboard
cd ~/.openclaw/workspace && python3 -m http.server 8082

# Terminal 2: start printer proxy (optional, for live stats)
python3 scripts/bambu_dashboard_proxy.py

# Open: http://127.0.0.1:8082/dashboard.html
# First time: enter WS URL + token (saves to localStorage)

What I Learned

Check for existing tools before building.
mudrii's dashboard saved several hours of analytics work. Five minutes of searching before dispatching Hands would have saved us building the wrong v2. The boring step is usually the important one.
Serve HTML over HTTP, not file://.
Any time you're doing WebSocket connections or have CORS concerns, python3 -m http.server is your fastest friend. file:// origins get rejected everywhere.
MJPEG streams need fetch-based health checks.
img.onload / img.onerror is not reliable for live video streams. Poll with fetch and an AbortController timeout. Decouple the display from the status.
Iterate on what exists. Don't rewrite.
dashboard_v2.html was technically complete. It was also the wrong design. The existing dashboard.html just needed bug fixes. Knowing when to stop building and start fixing — that's the real skill.
Route cheap work to cheap models.
Token optimization isn't just a cost concern — it's a system design question. Which tasks actually need expensive reasoning? Wire your UI as a routing layer, not just a viewer.

The dashboard is live. The printer is printing. The camera is watching. And when I hit record for TikTok, it looks like exactly what it is: a real operation, running in real time, managed by AI agents that know which problems are theirs.

That was the goal.
